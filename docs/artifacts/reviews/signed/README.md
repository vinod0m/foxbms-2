# Signed review packets land here

**This directory is for completed, signed review packets. It is not generated,
and nothing in it may be written by a tool.**

Every packet under `docs/artifacts/reviews/packets/` carries an empty signature
block, because a signature is a human act and this corpus will not let a process
imitate one. The generator has no code path that writes a decision, an approval
field, a signature or an execution verdict; `corpus.py selftest` reads all 321
generated packets in both formats on every run and fails if any of the seven
signature fields carries a value.

## Where a signed packet goes

1. Take the packet from `docs/artifacts/reviews/packets/<profile>/<id>.md`.
2. Answer its section 7 in your own copy.
3. Fill section 9 in your own copy.
4. Put the signed copy here, under the same `<profile>/` subdirectory, with the
   same filename. Keep it byte-for-byte as you signed it: the sha256 in its
   section 2 is the digest of the *record*, and the packet is the evidence that
   those are the bytes you read.

## Why not sign in place

`docs/artifacts/tools/make_review_packets.py` **refuses to overwrite a packet that
already carries a signature** and says where to move it, rather than destroying
it. That guard is tested - `corpus.py selftest` runs the generator, injects a
signature into a generated packet, runs the generator again, and asserts the
signature survived.

The guard exists because regeneration is routine. A corpus that regenerates its
review material weekly and stores signatures beside the generated material will
lose every approval it has ever collected, silently, within one cycle. This
directory is the separation that makes the guard unnecessary in the common path.

## THIS DIRECTORY IS NOW THE ONLY ADMISSIBLE HOME - ENFORCED, NOT ADVISED

As of 2026-10-04, amendment `APPROVAL-LEDGER-A1`, an approval citing a packet
under `docs/artifacts/reviews/packets/` **fails validation**. The finding names
this archive and says to archive the signed packet first. Until that amendment the
validator accepted either location while the packets *told* reviewers to use this
one - guidance implemented as a permissive rule, which is how a signed packet
ended up in a tree that regeneration overwrites.

That tree **is** regenerated by `make_review_packets.py`. The generator refuses to
overwrite a packet that already carries a signature, so evidence parked there
survives by ordering luck rather than by rule - and when it is finally
overwritten, the approval fails element 5 for a reason that has nothing to do with
the reviewer's judgement. This directory is the separation.

## What gets recorded, and where

A signed packet is evidence, not the record. The **decision** is recorded in an
append-only ledger, and the record keeps only a reference to it. The
machine-readable contract is
`docs/artifacts/governance/role-and-review-policy.json#/approval_ledger_contract`
(amendment `APPROVAL-LEDGER-A1`, which supersedes element 6 of
`#/approval_evidence_contract` and tightens element 5); the validator implements
it exactly and section 8 of every packet restates it for the reviewer.

**In `docs/artifacts/governance/approval-ledger.jsonl`** - one JSON object per
line, append-only, currently **0 bytes** because this corpus holds no approval:

`ledger_id`, `record_id`, `profile`, `kind`, `approved_record_sha256`,
`approved_content_revision`, `approved_by`, `role`, `independence`, `date`,
`signed_packet{path, sha256}`, `packet_first_commit`, `previous_entry_sha256`.

Each entry binds to its predecessor by digest, so deleting, reordering or editing
any entry breaks the chain from that point on, and `corpus.py` reports the
**first** break. **Append; never repair.** To record a changed judgement, add a
new entry.

**On the record** - three things, and nothing else:

1. `human_approval_status`: `approved` or `rejected` (both are recorded human
   decisions and both need a person behind them);
2. an `approval_evidence.human_approval` block carrying the six required
   elements, of which these five live here:
   - `approved_by` - a named **person**, not a role and not a team;
   - `role` - a `role_id` declared in `role-and-review-policy.json` - plus
     `independence{owner_role, satisfied, evidence, policy_ref}`, where
     `owner_role` must equal **this record's own** `owner_role`. Independence is
     then enforced rather than asserted: the approving role must differ from
     `owner_role` **and** from the author of the last content revision;
   - `date` in ISO-8601;
   - `review_packet{path, sha256, record_sha256_at_signing}` - `path` **must
     cite a packet under this directory**, `sha256` must equal that file's bytes
     as they stand now, and `record_sha256_at_signing` must equal **that
     packet's own** `integrity.record_sha256`;
   - and the grant value itself;
3. **`approval_ledger_ref{ledger_id, entry_sha256}`**, naming the line appended
   above.

**And NOTHING in `revision_history`.** This is the one instruction here that is a
hard rule rather than a convention. A `revision_history` entry *is* a content
change, so recording an approval through one forces the record's revision to bump -
which makes every link pinning that revision stale and invalidates the `sha256`
that every review record stores for it. An approval recorded that way produces a
signed approval and a corpus that no longer validates, with the two failures
having nothing obviously to do with each other. `approval_ledger_ref` is approval
**metadata**, excluded from the record's content digest, so recording it neither
bumps the revision nor stales a link nor invalidates a review digest. Proven by a
self-test, on a record a review record already covers.

Also unchanged: `automated_review_status` (machine checks, not human judgement);
`production_authorized` and `product_verification_credit` stay `false`. Granting
production authority additionally requires an approving role that holds it
(`architect` or `safety_manager`), a record family human approval is required for
(`safety_case`, `post_development_record`, `change`), and **its own ledger
entry** - one reference per kind, because a human approval and a production grant
are different claims.

`python3 docs/artifacts/tools/make_review_packets.py --transcribe <ID>` prints the
block, the ledger entry and the reference, with everything machine-readable
already resolved, writing nothing and appending nothing. **Run it twice**: the
digest an approval must cite is the digest of *this* archived copy, which has your
signature in it and therefore cannot be known before you have signed. The first run
tells you to archive first; the second resolves the digest from the file on disk.

**Recording the first approval no longer fails validation.** As of 2026-10-04,
amendment `APPROVAL-RULE-A1` replaced the blanket prohibition with the evidence
requirement above, and `APPROVAL-LEDGER-A1` gave that requirement a home where it
can actually be satisfied. A properly evidenced approval is accepted and the
acceptance suite stays green. What neither amendment did is produce one: every
record in this corpus is still `pending` and the ledger is **empty**, and writing
an approval value needs a person. If a finding arrives naming an unmet element,
fix that element - do not remove the approval.

## What this directory does NOT prove

It holds packets. It does not attest that anybody read the record in one.

**The hash chain proves existence, ordering and integrity. The git anchor proves
when and in what state the packet was committed. Neither proves that a human read
anything, and none of this makes an approval unforgeable.** A determined person
can write all six elements, archive a packet here, cite a real commit and maintain
the chain correctly, and nothing in this repository can distinguish that from a
real approval. That limit is irreducible. See
`docs/artifacts/governance/approval-ledger.md`.

## Rules for this directory

- **No generator may write here.** `make_review_packets.py` does not, by design.
  It is also the only place a signed packet is admissible from, which is why that
  rule matters rather than merely tidies.
- **No packet here may be edited after signing.** A corrected packet is a new
  document with a new signature, not an edit to a signed one.
- **A signed packet is never deleted.** A corpus that deletes the record of an
  approval it granted cannot show that it ever granted one - the same rule this
  corpus applies to finding records, which are never deleted either.
